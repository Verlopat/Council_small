# VRF Security-Game Reference Notes (RFC 9381)

**Source:** Goldberg et al., *Verifiable Random Functions (VRFs)*, RFC 9381,
August 2023. Official text: https://www.rfc-editor.org/rfc/rfc9381.html

**Scope and provenance:** These are concise, independently authored
paraphrases of Sections 3.1, 3.3 and 3.4, **not verbatim RFC quotations**.
RFC 9381 primarily specifies RSA- and elliptic-curve-based VRFs; its security
definitions provide a reference for a lattice-VRF design but do not prove any
lattice construction or reduction.

## Honest-evaluation correctness

An honestly generated public/secret key pair and honest evaluation/proof for a
valid input must cause the verifier to accept the associated output. An
adversarial attempt to find another accepted output is a *uniqueness* question,
not the standard honest-evaluation correctness requirement.

## Full uniqueness — Section 3.1

The adversary may select a VRF public key and a common input and attempt to
exhibit two proofs that verify for *different outputs* on that one input. In
particular, an honestly generated public key is **not** a required restriction.
A game about beating a fixed challenger-issued output does not by itself state
this full-key quantification.

## Full collision resistance — Section 3.2

Distinct inputs must not have the same valid VRF output under the same
public key. A failure on two different inputs with an identical output is a
collision-resistance attack, **not** a uniqueness attack. The same principle
holds for trusted collision resistance with honestly generated keys.

## Trusted uniqueness — Section 3.3

The key pair is generated by the prescribed honest key-generation procedure
and then given to the adversary. Uniqueness is required under this key-origin
assumption, even if the adversary knows both public and secret keys. A special
trapdoor oracle is not the definition. This is strictly a weaker requirement
than full uniqueness under malicious key generation.

## Pseudorandomness — Section 3.4

The adversary is given the public key and may obtain the genuine output and
corresponding proof for other inputs. It nominates a fresh challenge input
that it is barred from querying to the evaluation oracle. The challenge reveals
the *output only* (not the proof). Its distribution is either the real VRF
output or a uniformly random element of the output space; the adversary tries
to distinguish the two cases. Full vs selective pseudorandomness differs in
when the challenge input must be selected.

## Interpretation constraints

- Finding text that resembles these notes does **not** mechanically verify
  a security definition, establish semantic entailment, or prove a theorem.
- Definitions must specify exact domains, key-validation policies,
  challenge-oracle interfaces, allowable queries, adversary resources, and
  advantage parameters when used in formal proofs.
- A lattice VRF still needs scheme-specific reductions (e.g., to LWE or SIS
  if appropriate), not a generic statement that lattice hardness is enough.
- The Council's automated warnings are incomplete heuristics. Both positive
  and negative findings require independent human/formal review.
